# 系统设计评审（2026-11）

评审范围：架构、数据模型、业务规则、合规（GMP / ISO 13485 / 21 CFR Part 11）、安全、性能、集成与运维。
结论先行：**整体架构方向正确，核心合规控制已经落在后端强制执行；但距离正式用于受监管生产，还有 9 个必须先解决的问题（P0）**，
其中多数改动量不大。下文每条都标注了问题、影响、建议方案与工作量（S ≤ 1 天，M 2–5 天，L > 1 周）。

---

## 一、做得好的地方（保持）

| 设计 | 价值 |
|---|---|
| 模块化单体 + 单一 PostgreSQL | ERP/MES/WMS/QMS 同库同源，无接口、无对账；按领域分模块，将来可拆 |
| 规则在后端强制执行，前端只是“引导” | 绕过界面直接调接口也无法违规（如未放行发货、跳站、用过期仪器） |
| 工单下达时快照 BOM / 工艺 / 测试规格 | 工程变更不影响已下达批次，DHR 可还原当时的受控版本 |
| 库存质量状态（待检/合格/不合格/冻结）+ 货主维度 | 用“状态”而非“库位”实现隔离，规则简单可靠；客供料天然隔离 |
| 库存只经过一个服务变动，余额与流水同事务 | 杜绝“账实不符”类问题 |
| 审计追踪在数据访问层统一实现 | 新功能自动具备审计，不依赖开发人员自觉 |
| 端到端测试覆盖关键合规规则 | 规则回归有保障（迁移对等性也靠它验证） |

## 二、P0：上线前必须解决

### P0-1 两套后端并存（迁移收尾）　工作量：进行中
- **问题**：仓库里同时有 Python（`backend/`）和 NestJS（`server/`）两套后端；金蝶登录只在 NestJS 中实现。
- **影响**：两边行为可能分叉，维护成本翻倍。
- **方案**：完成迁移 → 用原 Python 测试对新后端做对等性验证 → 删除 Python，`server/` 改名为 `backend/`。

### P0-2 并发写入：库存重复行、工单计数丢失　工作量：S
- **问题**：（a）`wms_stock` 以（物料、库位、批次、状态、货主）定位一行，但数据库没有唯一约束，两个事务同时给同一个新批次入库会各自插入一行；
  （b）多个工位同时报工时，工单的完工数、工序合格数是“读-改-写”，没有行锁会丢失更新。
- **影响**：出库只扣其中一行，可能误报“库存不足”；工单完工数偏少、该完工的工单没有自动完工。
- **方案**：（a）加唯一索引 `UNIQUE NULLS NOT DISTINCT (material_id, location_id, lot_no, status, owner_customer_id)`（PostgreSQL 15+），入库改为 `INSERT … ON CONFLICT DO UPDATE`；
  （b）NestJS 版的报工、批量报工、完工入库、DHR 放行已先锁定工单行（`FOR NO KEY UPDATE`，并发测试验证过）；**NCR 处置（报废时更新工单报废数）仍需补同样的锁**。

### P0-3 多币别金额直接相加　工作量：S–M
- **问题**：客户有 USD、CNY 两种币别，驾驶舱“在手订单金额”把 1,760 USD 和 42,000 CNY 加成了“¥43,760”。应收账龄同样没有区分币别。
- **影响**：管理层看到的经营数据是错的。
- **方案**：短期按币别分别汇总；中期增加汇率表，统一折算为本位币（CNY）展示。

### P0-4 车间共用工位终端，操作人归属不可靠　工作量：M
- **问题**：工位电脑通常长期登录一个账号，换班后其他人继续用，报工和测试记录会记在错误的人名下；登录令牌 12 小时有效，也没有空闲超时。
- **影响**：违反 Part 11 / GMP 对“记录可归属到具体人员”的要求，这是审核中最常见的发现项之一。
- **方案**：工位终端支持**刷工牌（或工号 + PIN）切换当前操作员**，每次报工记录实际操作人；终端空闲 N 分钟自动锁定；办公端也增加空闲超时。

### P0-5 职责分离不足：管理员和厂长能做质量签名　工作量：S
- **问题**：`admin`、`manager` 角色包含 `qa` 权限，可以放行 DHR、处置 NCR、批准让步接收。
- **影响**：GMP 要求质量放行由质量部门独立负责；系统管理员不应能签署质量记录。
- **方案**：质量类电子签名（放行、NCR 处置、让步、CAPA 关闭）只允许 `qa` 角色；`admin` 只管账号与配置，不含业务权限。

### P0-6 工程变更只有工程师单人签名　工作量：M
- **问题**：BOM / 工艺路线（含测试规格上下限）由工程师一人签名即发布。
- **影响**：测试规格直接决定产品是否合格，GMP 要求变更须经质量部门评审批准。
- **方案**：发布改为两步：工程师“提交”（签名：编制）→ QA“批准”（签名：批准）后才生效；ECN 记录变更原因和影响评估。

### P0-7 审计追踪在数据库层可被修改；批量写入未覆盖　工作量：S
- **问题**：（a）审计表在数据库层面没有保护，有数据库权限的人可以改删；（b）审计钩子覆盖 `create/update/upsert/delete/updateMany/deleteMany`，但**没有覆盖 `createMany`**（目前代码没用到，属于潜在漏洞）。
- **方案**：应用数据库账号撤销 `sys_audit_log` / `sys_esignature` / `wms_stock_move` 的 UPDATE、DELETE 权限（或加触发器拒绝）；审计行增加前一行哈希形成链，可检测篡改；钩子补上 `createMany`（或在规范中禁止使用）。

### P0-8 金额用浮点数存储　工作量：M
- **问题**：数量和金额都是 Float（双精度）。数量问题不大，但金额累加会出现分位误差。
- **方案**：金额字段改为 `Decimal(18,2)`；数量可保留 Float 或改为 `Decimal(18,4)`。

### P0-9 备份与记录保存　工作量：S（配置）
- **问题**：没有定义备份、恢复和数据保存策略。医疗器械生产记录须长期保存（不少于产品寿命期，且自放行起不少于 2 年，以企业质量体系规定为准）。
- **方案**：PostgreSQL 每日全量备份 + WAL 归档（支持任意时间点恢复），异地保存；每季度做一次恢复演练并留记录。

## 三、P1：试运行期间完善

| # | 问题 | 影响 | 建议方案 | 工作量 |
|---|---|---|---|---|
| 1 | **返工换件不记录**：返工时更换的零件（如驱动 IC）没有登记批次 | 单台追溯不完整 | 返工报工时登记“拆下/装上”零件批次或 SN，并自动补领料 | M |
| 2 | **DHR 只能整单放行**：工单全部完工才能放行发货 | 大工单无法分批出货 | 支持按“放行批”（同工单内的子批）放行 | M |
| 3 | **没有单位换算**：LED 按卷采购、按颗领用 | 采购、仓库只能手工换算 | 物料增加采购单位/库存单位及换算率 | M |
| 4 | **批次属性分散在每条库存行上** | 有效期等修改要改多行，容易不一致 | 新增批次主数据表（物料 + 批号唯一），库存引用它 | M |
| 5 | **MRP 不分时段**：一次性汇总净需求；子件需求日期没扣父项生产周期 | 交期紧时建议不准 | 按周分桶展开，逐层扣减生产/采购提前期 | M–L |
| 6 | **IQC 检验项目是固定模板**；无 COA 附件；未实现 GB/T 2828.1 加严/放宽转移规则 | 检验依据不受控 | 按物料维护检验规范（受控版本）；附件；按历史批次自动转移 | M |
| 7 | **人员资质未校验**：任何操作员都能做任何工序 | GMP 要求人员经培训合格上岗 | 培训/上岗资质矩阵，工位报工时校验 | M |
| 8 | **缺少逆向流程**：生产退料、客户退货（RMA）、客诉、不良事件 | 售后追溯与 CAPA 输入缺失 | 补退料单、RMA、客诉登记并关联 NCR/CAPA | L |
| 9 | **没有附件存储**：缺陷照片、校准证书、COA、送货单 | 证据只能放线下 | 对象存储（MinIO/OSS）+ 附件表，挂在任意单据上 | M |
| 10 | **没有与金蝶财务的持续对接**：出入库、应收应付需要在金蝶重复录入 | 双录、易错 | 通过金蝶云星空 WebAPI 推送应收单/应付单/出入库单（或生成凭证），每日对账 | L |
| 11 | **账号安全**：密码只要求 6 位、不过期；登录锁定计数只在单个进程内存中 | 多实例部署时锁定失效 | 密码复杂度与有效期策略；锁定状态存数据库/Redis | S |
| 12 | **传输安全**：金蝶登录时密码经过本系统；内网常用 HTTP | 密码明文传输 | 本系统与金蝶均启用 HTTPS；令牌改为 HttpOnly Cookie 并加 CSP | S |
| 13 | **状态字段是自由字符串** | 拼写错误无法在数据库层发现 | 改为 Prisma enum 或 CHECK 约束 | S |

## 四、P2：规模化之后

| 问题 | 建议 |
|---|---|
| 驾驶舱和追溯在内存中循环统计、存在 N+1 查询 | 数据量上来后改为聚合 SQL / 物化视图，追溯接口批量查询 |
| 只支持单工厂、单组织 | 有多工厂规划时尽早加入“组织/工厂”维度（越晚加改造越大） |
| 测试数据靠手工录入 | 光谱仪、安规仪联网自动采集（这部分适合用 Go 写独立采集网关） |
| 没有标签打印、PDA | GS1 DataMatrix 标签打印、PDA 收发货 |
| 前端首屏体积偏大（ECharts 全量引入约 340KB gzip） | 按需引入 ECharts 组件、路由级拆包 |
| 文件型受控文件（SOP、图纸）不在系统内 | 与文控系统集成，或增加文控模块 |

## 五、建议的推进顺序

1. 完成 NestJS 迁移与对等性验证（P0-1）。
2. 同一轮修复数据层问题：P0-2 唯一约束、P0-7 审计保护、P0-8 金额精度、P0-3 币别（一次迁移完成）。
3. 权限与签名：P0-5 职责分离、P0-6 双人签名发布、P0-4 工位刷卡切换。
4. 上线准备：P0-9 备份演练 + 计算机化系统验证（URS/IQ/OQ/PQ）。
5. 试运行期间按业务优先级推进 P1，建议先做 1（返工换件追溯）、2（分批放行）、3（单位换算）、10（金蝶财务对接）。
